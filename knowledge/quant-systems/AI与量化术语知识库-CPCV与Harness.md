# AI与量化术语知识库：CPCV 与 Harness Engineer

## 0. 先给结论

### CPCV 是什么？

**CPCV = Combinatorial Purged Cross-Validation，组合式净化交叉验证。**

它是量化和时间序列建模里一种更严格的样本外评估方法，核心目的不是“让分数更好看”，而是：

1. **减少时间序列里的数据泄漏**；
2. **避免只在一条样本外路径上看起来有效**；
3. **让你看到策略/因子在多种市场片段组合下是否还站得住**。

一句最通俗的话：

> CPCV 不是只看“这一次样本外行不行”，而是看“换很多种样本外切法后，你是不是大多数时候都还行”。

### Harness Engineer 是什么？

`harness` 原义是“线束 / 套具 / 把很多部件接成一套能稳定工作的装置”。  
在软件、AI、量化里，`harness` 更接近：

> **测试线束 / 评测框架 / 实验驱动框架**

所以 `harness engineer` 不是“做模型的人”，而是：

> **把模型、策略、智能体、回测、评测、回归测试这一整套“怎么测、怎么比、怎么晋级”做工程化的人。**

如果放在 AI 语境，它更像 **evaluation engineer / experiment engineer / benchmark engineer**。  
如果放在量化语境，它更像 **评测线束工程师 / 回测评测框架工程师**。

---

## 1. CPCV 详细解释

## 1.1 为什么会有 CPCV？

因为量化和时间序列问题，天然不适合直接套普通机器学习里的随机交叉验证。

### 原因 1：时间顺序不能乱

金融数据不是 i.i.d.（独立同分布）样本。  
今天和明天、上周和下周，是强相关的。

如果你把样本随机打散再做 KFold，很容易出现：

1. 训练集里已经看到了和测试集高度相邻、甚至重叠的信息；
2. 标签窗口有交叉；
3. 持仓期或事件效应从训练穿透到测试；
4. 回测结果被“未来信息”污染。

### 原因 2：单一路径样本外很容易运气好

很多策略不是“真的稳”，只是恰好踩中了某一段市场。

如果你只做一条 walk-forward 样本外路径，容易出现：

1. 只在一个市场 regime 里有效；
2. 恰好在那段时间风格占优；
3. 你把一个偶然结果误判成稳定能力。

所以需要一种方法，不只看一条 OOS 曲线，而是看**很多条 OOS 路径的分布**。  
这就是 CPCV 出现的原因。

---

## 1.2 CPCV 的名字到底是什么意思？

### C = Combinatorial（组合式）

不是只切一种训练/测试方式，而是：

1. 把整段时间切成 N 段；
2. 每次选 k 段当测试集；
3. 穷举或遍历多种测试组合；
4. 得到很多条样本外路径。

### P = Purged（净化）

训练集里凡是和测试标签窗口有重叠、可能泄漏信息的样本，要删掉。

### CV = Cross-Validation（交叉验证）

本质上它还是一种交叉验证，只是专门为**时间序列和金融场景**做了加强版设计。

---

## 1.3 CPCV 是怎么做的？

一个最标准的理解流程是：

1. 把整段时间序列切成 `N` 个连续时间块；
2. 每次从中选 `k` 个时间块作为测试集；
3. 剩余时间块作为训练集；
4. 对训练集做 `purge`，删掉与测试标签窗口重叠的样本；
5. 对测试集前后做 `embargo`，留缓冲期，避免持仓影响或事件影响穿透；
6. 遍历多种测试块组合；
7. 最终不是得到一个 OOS 结果，而是得到一组 OOS 分布。

---

## 1.4 什么是 Purge？

### 直觉理解

如果你的标签是“未来 5 天收益”，那测试集里某个样本的标签，其实会用到未来几天的数据。  
如果训练集中刚好有和这几天重叠的样本，模型就有可能“偷看”到了测试标签相关的信息。

`purge` 做的事就是：

> **删掉训练集中那些和测试集标签窗口重叠的样本。**

### 一个简化例子

假设：

1. 你的标签是未来 10 个交易日收益；
2. 测试集从 2024-01-01 开始；
3. 训练集中靠近这个时间点的样本，其标签窗口可能已经碰到测试区间。

这时就不能保留这些训练样本，因为它们已经和测试“共享未来”了。

---

## 1.5 什么是 Embargo？

`embargo` 是**缓冲期**。

它解决的是另一类问题：  
即使训练标签没有直接和测试重叠，测试区间前后也可能因为持仓延续、事件影响、调仓影响而互相污染。

所以在测试区间前后，会额外空出一段时间不参与训练。

### 一句话理解

`purge` 是删掉“明确重叠”的样本；  
`embargo` 是防止“边界附近的隐性影响”穿透。

---

## 1.6 CPCV 比 Walk-forward 强在哪？

### Walk-forward

优点：

1. 简单；
2. 便宜；
3. 很符合真实时间推进方式。

缺点：

1. 只有少数几条测试路径；
2. 很容易受某一段市场 regime 影响；
3. 容易把偶然样本外当成稳定能力。

### CPCV

优点：

1. 看的是**一组 OOS 分布**，不是单条曲线；
2. 更能发现策略是不是只在某种市场环境有效；
3. 更能压制时间泄漏和标签泄漏；
4. 更适合作为“晋级门禁”的严格标准。

缺点：

1. 实现更复杂；
2. 计算更贵；
3. 需要你先定义好 purge / embargo / 标签窗口。

### 什么时候用 Walk-forward，什么时候上 CPCV？

1. **策略初筛 / 快速试验**：先用 walk-forward。
2. **候选策略验收 / 晋级门禁**：上 CPCV。
3. **你对一个结果特别兴奋时**：更应该上 CPCV，不然最容易被假阳性骗。

---

## 1.7 CPCV 到底看什么输出？

真正用 CPCV 时，不该只看一条收益曲线，而是看这些指标的**分布**：

1. OOS 年化收益分布；
2. OOS Calmar 分布；
3. OOS Sortino 分布；
4. OOS 最大回撤分布；
5. OOS win rate（打赢 baseline 的路径比例）；
6. 执行折损后的稳定性；
7. 极端 path 下是否崩掉。

### 一个朴素的验收口径

至少要回答这几个问题：

1. 大多数 OOS path 都打赢 baseline 吗？
2. 中位数表现是否稳定高于 baseline？
3. 最差 25% path 会不会难看得不可接受？
4. 加入交易成本、滑点和容量后是否还站得住？

如果只有均值好看，但尾部很烂，那不是稳健策略，只是“看起来平均不错”。

---

## 1.8 CPCV 容易被误解的地方

### 误解 1：CPCV 是为了把分数做得更高

恰恰相反。  
CPCV 通常会把很多原本“看起来不错”的东西打回原形。

### 误解 2：有了 CPCV 就绝对不会过拟合

不是。  
CPCV 只能**降低**你被样本外错觉骗到的概率，不能替代：

1. 合理假设；
2. 数据质量控制；
3. 成本建模；
4. 容量分析；
5. 失败复盘。

### 误解 3：CPCV 适合所有阶段

也不是。  
如果你在很早期就对每个小想法都跑全量 CPCV，成本会太高。  
它更适合用在：

1. 候选策略收缩后；
2. 准备晋级 paper / shadow / prod 前；
3. 你要给“能不能继续投入资源”做硬判断的时候。

---

## 1.9 你该怎么理解 CPCV 的价值？

一句最重要的话：

> CPCV 不是一个“更复杂的回测技巧”，它是一种**反自欺机制**。

你做它，不是为了证明自己对，而是为了更早发现自己可能错。

---

## 2. Harness / Harness Engineer 详细解释

## 2.1 Harness 到底是什么意思？

`harness` 在软件工程里常见于 `test harness`：

> 一套把被测对象、输入数据、执行环境、评测指标和输出报告串起来的测试框架。

所以在 AI / 量化里，`harness` 更接近：

1. 评测线束；
2. 实验驱动框架；
3. 回归测试框架；
4. benchmark / eval pipeline。

它不只是“运行一下代码”，而是：

> 把“怎么公平地测、怎么稳定复现、怎么自动比较、怎么决定晋级”做成标准化系统。

---

## 2.2 什么是 Harness Engineer？

最直白的定义：

> **Harness Engineer = 负责把评测、实验、回归、晋级门禁做工程化的人。**

他不一定发明最强模型，也不一定直接写策略 alpha；  
但他负责保证：

1. 模型/策略被测得对；
2. 测试过程可复现；
3. 不同版本可比较；
4. 结果不是靠感觉判断；
5. 新方案不会悄悄破坏旧系统。

---

## 2.3 在 AI 语境里，Harness Engineer 具体做什么？

如果是 AI / 大语言模型 / 智能体 场景，Harness Engineer 常做这些：

1. 定义评测任务；
2. 准备 benchmark 数据集；
3. 统一 prompt / tool / environment 配置；
4. 固定随机种子、模型版本、系统版本；
5. 设计指标：准确率、成功率、耗时、成本、稳定性、安全性；
6. 做回归测试：新模型不能把旧能力搞坏；
7. 做 leaderboard 或 gate：promote / canary / rollback；
8. 做失败归因：是模型错、工具错、环境错，还是评测协议错。

### 你可以把它理解成

**AI 里的“模型测试平台 + 实验治理 + 结果裁判系统”**。

---

## 2.4 在量化语境里，Harness Engineer 具体做什么？

如果是量化语境，它会变成：

1. 定义训练 / 验证 / 测试切分方式；
2. 定义 walk-forward / CPCV / purged split；
3. 定义成本、滑点、容量、涨跌停、停牌等仿真规则；
4. 定义评价指标：Calmar、Sortino、CVaR、worst5d、OOS win rate；
5. 保证实验 artifact 可复现；
6. 让新因子、新策略、新执行逻辑自动和 baseline 对比；
7. 决定一个候选到底该 promote、shadow 还是 reject。

### 一句话理解

量化里的 Harness Engineer，负责的是：

> **把“怎么测策略”变成一套标准协议，而不是每次靠研究员拍脑袋。**

---

## 2.5 Harness Engineer 和下面这些岗位有什么区别？

### vs Research Engineer

Research Engineer 更偏：

1. 搭研究流程；
2. 支持建模和实验；
3. 贴近研究员需求。

Harness Engineer 更偏：

1. 定义评测协议；
2. 管实验公平性；
3. 管回归、复现、晋级门禁。

### vs Model Engineer / MLE

MLE 更偏：

1. 训练模型；
2. 部署模型；
3. 优化 serving。

Harness Engineer 更偏：

1. 搭评测框架；
2. 做回归体系；
3. 保证新模型/新策略被测得对。

### vs Platform Engineer

Platform Engineer 更偏底座和基础设施。  
Harness Engineer 更偏“评测与实验的业务协议工程化”。

很多团队里这几个角色会重叠，但重心不同。

---

## 2.6 为什么 Harness Engineer 很重要？

因为模型和策略世界里，最危险的不是“你没有好想法”，而是：

1. 你测错了；
2. 你没控制好泄漏；
3. 你每次评测口径不一致；
4. 你没法稳定复现；
5. 你不知道失败原因；
6. 你把偶然的好结果晋级了。

所以 Harness Engineer 的价值不是“让分数更高”，而是：

> **让团队更少自欺，更少误判，更少把资源浪费在假阳性上。**

---

## 2.7 你为什么应该特别重视 Harness 这个概念？

因为这其实和你的背景非常接近。

你过去做的很多事情，本质上就是 harness 思维：

1. 统一录制 / 回放；
2. 环境一致性；
3. 质量监控；
4. 问题复现；
5. 诊断流程；
6. 版本与流程治理。

只是过去这些事情发生在自动驾驶和 AIOT；  
现在如果迁移到 AI / 量化，它就会变成：

1. 评测线束；
2. 回测线束；
3. 回归框架；
4. 研究到上线的门禁系统。

所以你不是“第一次接触 harness 思维”，而是过去一直在做，只是名字不叫这个。

---

## 3. 你接下来该怎么做

## 3.1 如果你想往量化方向走

你应该做一个**最小量化 harness 项目**。

### 最小项目目标

拿一个简单策略或因子，不是只回测出一个收益图，而是做出一条完整评测线：

1. 数据版本固定；
2. train / validation / test 切分固定；
3. walk-forward 跑通；
4. CPCV 跑通；
5. 交易成本和滑点接入；
6. baseline 对比；
7. 输出统一报告；
8. 给出 promote / reject 结论。

### 你做出来后，面试时可以怎么说

我不只是写了一个因子或策略，我把这套策略评测线也搭了，包括时间序列切分、purge/embargo、CPCV、成本建模、baseline 对比和结果报告。我的重点不是追一条最好看的收益曲线，而是让候选能被更可靠地评估。

这句话会非常像 Harness Engineer。

---

## 3.2 如果你想往 AI / 智能体 方向走

你应该做一个**最小 AI eval harness 项目**。

### 最小项目目标

拿一个模型或 agent task，做出：

1. 固定数据集；
2. 固定 prompt / tool 配置；
3. 固定评测环境；
4. 自动跑多个版本；
5. 输出准确率 / 成功率 / 延迟 / token cost；
6. 做 regression compare；
7. 给出 promote / reject 结论。

### 这会训练你什么？

1. 指标意识；
2. 可复现意识；
3. 回归测试意识；
4. 失败归因意识；
5. “不是让它跑起来，而是让它被可靠评估”的意识。

---

## 3.3 如果你想把这两边连起来

那就把自己定位成：

> **evaluation-minded systems engineer（以评测与可信度为中心的系统工程师）**

这其实非常适合你。

因为你的天然强项不是“拍脑袋想一个最炫的模型”，而是：

1. 把复杂链路做稳定；
2. 把结果做可复现；
3. 把失败做可诊断；
4. 把流程做成规范。

这就是 harness 思维的核心。

---

## 4. 你最该记住的几句话

### 关于 CPCV

> CPCV 的本质，不是更复杂的验证法，而是防止自己被一条漂亮 OOS 曲线骗到。

### 关于 Harness Engineer

> Harness Engineer 的本质，不是发明模型或策略，而是把“怎么测它们”变成可靠、统一、可复现、可回归的系统。

### 关于你自己

> 你过去做的统一录制回放、时序一致性、诊断复现、流程治理，其实已经很接近 harness engineer 的思维方式。

---

## 5. 你下一步最具体的行动

如果只给你一个最实在的行动建议，就是：

1. **量化侧**：做一个最小 CPCV + baseline compare + 统一报告输出的策略评测线。
2. **AI 侧**：做一个最小 prompt / model / agent 的 eval harness。
3. **表达侧**：以后面试时，不只说“我会做系统”，而是说“我擅长把复杂系统做成可评测、可复现、可归因、可晋级的工程体系”。 

这句话会直接把你和普通“只会写功能的工程师”区分开。
